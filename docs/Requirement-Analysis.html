Table 3.2: Use Case Description in Login

ProcessLogin
DescriptionA security process that authenticates Faculty Users and Administrative Users and grants them access to their respective system portals based on the role stored in their account.
Desired OutcomeThe user is successfully signed in and redirected to the portal for their role: the Faculty portal for Faculty Users, the Administrative Dashboard for the Administrator and Department Chair, or the Program Chair Dashboard for Program Chairs.
ActorsFaculty User, Administrative User
Pre-conditionThe user must have a registered and active account in the system database. Faculty accounts are created by the Administrator through the Faculty records; Administrative accounts are created through Manage Accounts & Settings.
Scenarios
  • Select the account type: “Administrator / Chair” or “Faculty”.
  • Input the registered username (Faculty may also use a verified email address) and password, then click Sign In. Faculty Users may instead sign in with their verified Google account.
  • If Two-Step Verification is enabled and the device is not yet trusted, input the 6-digit verification code sent to the registered email.
  • The system validates the credentials, identifies the user role, and opens the corresponding portal.
Workflow
  1. The user opens the Login page and selects the account type.
  2. The user enters the username or email and password and clicks Sign In (or a Faculty User clicks Sign in with Google).
  3. The system verifies the credentials and confirms that the account is active (for Faculty, that the faculty record is also active).
  4. If Two-Step Verification is enabled and the device is not trusted, the system emails a 6-digit code and the user enters it.
  5. The system creates the session, remembers the device as trusted, and redirects the user to the portal of their role.
Post-conditionThe user gains access only to the features authorized for their role, and the sign-in is recorded in the audit trail.
Business Rule
  • Access is restricted based on role; the “Administrator / Chair” option accepts only Administrator, Department Chair, and Program Chair accounts, and the “Faculty” option accepts only Faculty accounts.
  • Five failed sign-in attempts within 15 minutes lock further attempts from the same network for 15 minutes.
  • Deactivated accounts cannot sign in.
  • Signing in with an email address, and Two-Step Verification, require a verified email address.
  • The verification code has 6 digits, expires after 5 minutes, allows at most 5 attempts, and can be resent after 60 seconds.
  • A trusted device skips the verification code for 30 days; a session expires after 30 days.
  • Google sign-in is available only to Faculty accounts linked to a verified Google email.

Table 3.3: Use Case Description in Manage My Account

ProcessManage My Account
DescriptionA process that allows a signed-in user to maintain their own account information and security settings, such as password, profile picture, Two-Step Verification, and trusted devices.
Desired OutcomeThe user’s own account details and security preferences are updated and take effect immediately.
ActorsFaculty User, Administrative User
Pre-conditionThe user must be logged in to the system.
Scenarios
  • Open Profile Settings (Faculty User) or My Account / Settings (Administrative User).
  • Change password: input the current password, the new password, and the password confirmation.
  • Upload or replace the profile picture (JPEG, PNG, or WebP image).
  • Turn Two-Step Verification on or off, and review or remove trusted devices.
  • Verify email ownership through Google; Faculty Users may also choose the Light or Dark display theme.
Workflow
  1. The user opens their account page from the navigation or profile menu.
  2. The user selects the section to update (password, picture, security, Google verification, or appearance).
  3. The user enters the required information and submits it.
  4. The system validates the input against the account rules.
  5. The system saves the change and displays a confirmation.
Post-conditionThe updated password, picture, or security preference is stored for the user’s account; after a Faculty password change, the account’s other trusted devices are signed out.
Business Rule
  • Users can change only their own account.
  • The current password is required to set a new password; the new password must be at least 8 characters, must match its confirmation, and must differ from the current password.
  • Faculty passwords must combine at least two of: uppercase letters, lowercase letters, numbers, and symbols.
  • Profile pictures must be JPEG, PNG, or WebP images under 5 MB; the file content is checked, not only the extension.
  • Two-Step Verification can be enabled only when the account email is verified, and turning it off requires a verification code.

Table 3.6: Use Case Description in Scan Room QR Code

ProcessScan Room QR Code
DescriptionA process that allows a Faculty User to scan the QR code posted at a room to record their presence and occupy the room for a scheduled class or, for lecture rooms, as a walk-in.
Desired OutcomeThe room is marked as Occupied by the Faculty User and the check-in is logged as On Time or Late, or the scan is rejected with the reason shown.
ActorsFaculty User
Pre-conditionThe user must be logged in as a Faculty User, the room must be active and have a generated QR code, and the device must allow camera access.
Scenarios
  • Open Scan QR Code and allow the camera.
  • Point the camera at the room’s QR code.
  • The system validates the scan and displays the result (occupied successfully, late check-in, or the reason it was blocked).
Workflow
  1. The Faculty User opens Scan QR Code and the camera starts.
  2. The camera reads the room QR code and the system identifies the room.
  3. The system checks whether the room is already occupied or reserved by another faculty member; if so, the scan is blocked.
  4. If a class is scheduled in the room at that time: the scan is accepted only for the assigned faculty, from 15 minutes before the start until the end of the class; it is On Time up to 5 minutes after the start and Late afterwards. A scan by another faculty is rejected and reported as unauthorized.
  5. If no class is scheduled, a lecture room that is free can be occupied as a walk-in; laboratory rooms can be occupied only during a scheduled class.
  6. The system marks the room as Occupied, logs the scan, and notifies the Administrative Users.
Post-conditionThe room occupancy and the scan log are recorded, and Room Monitoring shows the room as In Use.
Business Rule
  • A Faculty User can scan only for themselves.
  • An invalid QR code or an inactive room is rejected.
  • A room occupied for a scheduled class stays occupied until 30 minutes after the scheduled end time.
  • Scans after the class has ended are rejected (scan window closed).
  • Laboratory rooms follow the scheduled-session rules only; walk-in occupancy applies to lecture rooms.
  • Repeated scans of the same room are recognized and not recorded twice.

Table 3.7: Use Case Description in Manage Academic Setup

ProcessManage Academic Setup
DescriptionA process that allows Administrative Users to maintain the academic data used by workload and scheduling: curriculum subjects per program, faculty records, and class blocks.
Desired OutcomeThe curriculum, faculty records, and class blocks are up to date and ready for workload assignment and scheduling.
ActorsAdministrative User
Pre-conditionThe user must be logged in as an Administrative User and the programs must exist. Blocks can be created only after curriculum subjects exist for the selected program, year level, semester, and curriculum version.
Scenarios
  • Curriculum Setup: select the program and curriculum version; add, edit, or remove subjects (subject code, descriptive title, year level, semester, lecture hours, laboratory hours, credit units, prerequisites), or import subjects from an Excel file.
  • Faculty: add, edit, or delete faculty records (name, program, position/academic rank, employment status, designation and units, years in service, educational qualification, major, eligibility, specialization, priority subjects, blocks to teach, and login username, email, and password).
  • Block Creation: select the program, curriculum, year level, and semester, set the number of students, and create the next block; click + to create several consecutive blocks at once.
Workflow
  1. The user opens Curriculum Setup, Faculty, or Block Creation under Setup.
  2. The user selects the program and other required options and enters the record details.
  3. The system validates the required fields and uniqueness rules.
  4. The system saves the record. A new faculty record automatically receives a linked Faculty login account; a new block automatically receives all subjects of the selected curriculum, ready for assignment.
  5. The system displays the updated list.
Post-conditionThe academic records are saved; deleting a faculty record releases the subjects that were assigned to them.
Business Rule
  • Subject code, descriptive title, program, year level, and semester are required; the subject code must be unique per program, year level, semester, and curriculum version; hours and units cannot be negative; an import is limited to 1,500 subjects.
  • Faculty first name, last name, program, position, username, email, and password are required; the username and email must be unique; the password must be at least 8 characters; years in service must be 0–100.
  • Blocks are named A–Z in order without skipping, and all blocks of the same program, year level, and semester must use the same curriculum version.
  • Only the Administrator can add, edit, or delete faculty records; Program Chairs and Department Chairs can view them.
  • Program Chairs can create blocks only for their own assigned program; curriculum can be managed for all programs.

Table 3.8: Use Case Description in Manage Faculty Workloads

ProcessManage Faculty Workloads
DescriptionA process that allows Administrative Users to assign block subjects to faculty and classify each load as Regular Load, Overload, or Praise Load, including load deductions.
Desired OutcomeEach faculty member has a term workload within the allowed limits, and every assigned subject is ready for scheduling.
ActorsAdministrative User
Pre-conditionThe user must be logged in as an Administrative User; the active school year and semester must be set; faculty records and blocks must exist.
Scenarios
  • Select the faculty (filter by program and employment status) and review the current Regular Load against the limit.
  • Select an unassigned subject (grouped by block) and assign it; confirm Regular Load or Overload when prompted.
  • Move a subject, or only its lecture or laboratory component, to Overload or Praise Load, return it to Regular Load, or unassign it.
  • Record load deductions (e.g., designation or special assignment) and Praise Load entries.
Workflow
  1. The user opens Faculty Workload and selects a faculty member.
  2. The user selects a subject to assign.
  3. The system computes the subject value: for Permanent faculty, lecture hours + 0.75 × laboratory hours (units); for Contractual faculty, contact hours.
  4. The system compares it with the remaining regular capacity and asks the user to confirm assignment as Regular Load or Overload.
  5. The system saves the assignment, marks the subject as Assigned, and updates the workload totals.
Post-conditionThe faculty workload is recorded and the subject becomes available for scheduling.
Business Rule
  • A subject can be assigned to only one faculty member.
  • The subject’s block must be in the faculty’s Blocks to Teach for the term; a faculty member with no blocks listed may be assigned any block.
  • The Regular Load limit is 18.25 units less deductions for Permanent faculty and 30 hours for Contractual faculty.
  • Permanent faculty may carry at most 6.25 units of Overload per term.
  • Praise Load applies to Permanent faculty only, and its units and hours cannot be negative.
  • A subject in Praise Load must be returned before it can be moved to Overload.

Table 3.9: Use Case Description in Manage Class Schedules

ProcessManage Class Schedules
DescriptionA process that allows Administrative Users to set the day, time, and room of each assigned subject and to review the resulting Class Program, Master Schedule, and Faculty Schedules.
Desired OutcomeEvery assigned subject has a conflict-free schedule and room, reflected in the Class Program, Master Schedule, Faculty Schedules, and the faculty’s My Schedule.
ActorsAdministrative User
Pre-conditionThe user must be logged in as an Administrative User; the subject must already be assigned to a faculty member; rooms must be registered.
Scenarios
  • Select the program, block, and subject to schedule.
  • Choose the day pattern (e.g., Mon/Thu, Tue/Fri, Wed), the start time of each lecture or laboratory session, and the room.
  • The system checks for conflicts before saving.
  • Review the Class Program per block, the Master Schedule, and the Faculty Schedules.
Workflow
  1. The user opens Schedule Classes and selects a subject.
  2. The user enters the day pattern, session times, and room.
  3. The system validates the sessions and checks for faculty, block, and room conflicts, showing each conflict found.
  4. The system saves the sessions and marks the subject as Scheduled.
  5. The schedule appears in the Class Program, Master Schedule, Faculty Schedules, and the faculty’s My Schedule.
Post-conditionThe class sessions are saved and the subject status becomes Scheduled.
Business Rule
  • A faculty member must be assigned before a subject can be scheduled.
  • The total session hours must equal the subject’s required hours.
  • Sessions must be within 7:00 AM to 9:00 PM and must not overlap each other.
  • A session cannot conflict with another class of the same faculty, the same block, or the same room at the same time.
  • The room must be active; laboratory sessions require a laboratory room, lecture-only subjects cannot use a laboratory room, and a laboratory session may be saved without a room.

ProcessManage Accounts & Settings
